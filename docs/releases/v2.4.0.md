# v2.4.0

v2.3.0 뒤 `changelog.d/`에 쌓인 항목을 모은 것이다. 클라우드 세션이 머지 큐에 넣는 길(`github/enqueue.yml`)이 새로 생겨 minor를 올린다. 판 올리기는 [docs/start.md](../start.md) 「판 올리기」대로 `python3 -I .baseline/baseline.py upgrade v2.4.0`이다. 관리 블록·관리 파일은 `upgrade`가 바꾸므로 손으로 옮길 일은 거의 없다.

- 클라우드 세션도 `enqueue`로 머지 큐에 넣는다. `github/enqueue.yml`을 `.github/workflows/enqueue.yml`로 복사하고(workflow 권한이 바뀌므로 소유자가 병합), `upgrade`로 `enqueue-comment` 명령이 있는 판을 받는다. 로컬은 그대로다. 이 workflow가 없으면 클라우드의 `enqueue`는 그 사실을 알리고 멈춘다.
- 리뷰 지적마다 `재현함: <명령과 결과>` 또는 `불확실: <확인한 것과 까닭>`을 붙이게 하는 문장이 `REVIEW.md` 관리 블록에 생긴다(`upgrade`로 바뀐다). 프로젝트가 `prompts/review.md` 사본을 두면 4번 줄의 같은 문장을 손으로 옮긴다.
- `WORKFLOW.md`에 open-code-review를 어려움 PR의 선택 외부 리뷰 입력으로 쓰는 법과 한계(문서 파일 제외)가 적혔다. 옮길 일은 없다.
- 클라우드의 `review-report`도 리뷰 스레드를 해결한다(프록시의 `pulls/<번호>/ccr/` 경로). 그 경로가 거절하면 답만 달고 해결하지 못했다고 알린다. 소비 레포가 옮길 일은 없다. 다음 태그의 `upgrade`로 받는다.
- `REVIEW.md` 관리 블록의 Spec 기준에 문장이 더해진다(`upgrade`로 바뀐다). 동작을 바꿨는데 `baseline check` 통과만 적은 「실행 확인」은 비운 것으로 본다. 관리 바이트만 바꾼 upgrade PR처럼 프로젝트 동작을 바꾸지 않는 PR은 `없음: <이유>`로 쓸 수 있다. 소비 레포가 옮길 일은 없다.
- PR 템플릿 Review 칸에 「검토 범위:」 줄이 생기고 `review-report`가 이 줄과 지적의 `file:line`을 검사한다(`upgrade`로 바뀐다). `리뷰한 모델:` 아래에 `<검토한 수>/<PR의 변경 파일 수>`를 쓴다. 이미 열린 PR은 리뷰를 다시 쓸 때 줄을 더한다. 프로젝트 `REVIEW.md`·`prompts/` 사본이 있으면 같은 문장을 손으로 옮긴다.
- 소비 레포가 옮길 일은 없다. repo-baseline의 주간 `skills-bump --check`가 IP 허용 목록 때문에 토큰이 막힌 commit 출처(cursor/plugins)를, 토큰 없는 REST 대신 토큰 없는 git으로 읽는다. 공유 러너 IP의 REST 한도에 걸려 실패하던 것을 막는다.
- (v2.3.0에 이미 들어갔으나 그 노트에서 빠진 항목) 소비 레포가 옮길 일은 없다. repo-baseline의 주간 `skills-bump`가 IP 허용 목록을 켠 조직(cursor)의 공개 저장소를 토큰 없이 다시 읽어 Issue를 연다.
- 소비 레포가 옮길 일은 없다. pstack 스킬을 aaeb0ea로 올렸다(`arena`, `unslop` 본문이 바뀌고 나머지 다섯 스킬은 그대로다). 다음 태그의 `upgrade`로 받는다.
